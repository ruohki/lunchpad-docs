# Working on the Lunchpad docs

The site is [Astro Starlight](https://starlight.astro.build) with the Lunchpad look (the app's
stage palette, orange accent, Inter and JetBrains Mono). It expects the app checkout next to
the `lunchpad-extra` folder (`../../lunchpad` from here); point `LUNCHPAD_DIR` elsewhere if
yours lives somewhere else. Only syncing and screenshots need the app, building does not.

```bash
npm install                 # or bun install
npx playwright install chromium   # once, for screenshots
npm run dev                 # the site at http://localhost:4321
npm run build               # the static site in dist/
```

Node 22.18 or newer runs the TypeScript scripts in `scripts/` directly.

| Script | What it does |
| --- | --- |
| `npm run actions:sync` | Reads the app and writes `src/data/actions.json` (names, descriptions, icons, menu groups, Wait switch), then checks coverage |
| `npm run actions:check` | Only the check: every action has a page (`actionTypes`) and a screenshot, no page names a removed action |
| `npm run screenshots` | Takes every screenshot; `npm run screenshots -- playSound app/settings` takes only the ones whose name contains a word |
| `npm run app:demo` | Serves the app's interface with demo data at http://localhost:1430, to look around before writing a scenario |

## Layout

```
src/content/docs/
  getting-started/  guides/  help/      general pages
  actions/index.mdx                     overview, built from the app's data
  actions/<group>/<name>.mdx            one page per entry in the app's "Add action" menu
src/assets/screenshots/{actions,app}/   generated, do not edit by hand
src/data/actions.json                   generated by actions:sync
src/components/                         ActionHeader, ActionShot, AppShot, ActionIndex, …
src/styles/lunchpad.css                 theme (colours mirror the app's src/index.css)
scripts/screenshots/                    screenshot harness (see below)
```

Action groups follow the app's menu: `media`, `general`, `flow`, `system`, `stop`, and
`streaming` for OBS Studio and Streamlabs, whose twin actions share one page. Markers that come
as a set (Condition / Otherwise / End condition, Flip flop A / B / end, Push-to-talk on / off)
share the page of their menu entry.

## When a new action ships

1. In the app, follow `docs/ADDING_ACTIONS.md` of the Lunchpad repository.
2. `npm run actions:sync`. The action now appears on the Actions overview, greyed out until it
   has a page, and the check lists what is missing.
3. Add a scenario: one line in `scripts/screenshots/scenarios/actions.ts`, for example
   `shot("myAction", [act({ type: "myAction", … })])`. The action lands in the "When pressed"
   list of the button at column 1, row 8, the first row is unfolded and the list is captured.
   Options: `open` (rows to unfold), `wholeTab`, `button` (loop, released list, …), `then`
   (clicks before the capture, such as a test button), `scenario` (fake backend state).
4. If the editor asks the backend for something new (a list of devices, a test run), answer
   the command in `scripts/screenshots/mock/backend.ts` with demo data from `fixtures.ts`.
   Unhandled commands log `[mock backend] unhandled command …` in the browser console and
   return `null`.
5. `npm run screenshots -- myAction` and look at `src/assets/screenshots/actions/myAction.png`.
6. Write the page from the template below and put it in the group folder with the right
   `sidebar.order` (its position in the app's submenu). For the release that introduces it,
   add `badge: { text: New, variant: tip }` under `sidebar`.
7. `npm run actions:check` and `npm run build` must both pass.

When an editor changes, re-run its screenshot. When the app renames an action in `en.json`,
`actions:sync` updates the header of its page; check the prose for the old name.

`ActionHeader` shows the icon, the app's name and description, the menu path, the marker set
and the Wait badge from `src/data/actions.json`, so the prose does not repeat them. It fails the
build for an action type the app does not have. For the OBS / Streamlabs twins pass both types
and show both screenshots in `<Tabs syncKey="streaming-app">`.

## Writing

- Write for people who stream and automate, not for developers: plain words, second person,
  short paragraphs.
- Name things as the app does, in bold: **Add action**, **When pressed**, **Wait**. The
  labels are in the app's `src/i18n/en.json`; the app uses British spelling (colour).
- Only document what the app does. When in doubt, read the code (`src-tauri/src/macros/` for
  how actions run) rather than guess.
- Keys as `<kbd>Ctrl</kbd>`, platform steps in `<Tabs syncKey="os">` with "Windows" and
  "macOS". Links are absolute with a trailing slash: `/guides/variables/`.

## Publishing

The build in `dist/` is plain files: no server, no API routes, and search (Pagefind) is a static
index the browser loads. It is served from a bunny.net Storage Zone behind a Pull Zone.

`.github/workflows/docs.yml` checks and builds every push and pull request. A tag starting with
`v` also publishes that exact build:

```bash
git tag v1.0.1 && git push origin v1.0.1
```

`scripts/deploy-bunny.ts` uploads every file (with a SHA-256 checksum), then deletes what the
build no longer has, so the live site never misses a file mid-deploy, and finally purges the Pull
Zone's cache. It also puts the 404 page at `bunnycdn_errors/404.html`, where Bunny looks for a
custom error page. `node scripts/deploy-bunny.ts --dry-run` shows what a deploy would change.

Repository settings (Settings → Secrets and variables → Actions):

| Name | Kind | What |
| --- | --- | --- |
| `BUNNY_STORAGE_PASSWORD` | secret | Storage Zone → FTP & API Access → Password |
| `BUNNY_STORAGE_ZONE` | variable | Storage Zone name, `lunchpad-docs` |
| `BUNNY_STORAGE_HOST` | variable | Regional endpoint, `storage.bunnycdn.com` for Falkenstein |
| `BUNNY_API_KEY` | secret | Account → API key; with the next one, deploys purge the CDN cache |
| `BUNNY_PULLZONE_ID` | variable | The Pull Zone's id (in its URL in the dashboard) |
| `SITE_URL` | variable | Public address, e.g. `https://docs.example.com`; turns on the sitemap |

Without the two purge settings a deploy still works, but pages already cached at the edge stay
old until they expire, and the Pull Zone sends `max-age=2592000`: up to 30 days. Set
`BUNNY_API_KEY` and `BUNNY_PULLZONE_ID` so every deploy purges, or purge by hand in the bunny.net
dashboard after a deploy.

## How the screenshots are made

`scripts/screenshots/serve.ts` starts Vite on the app's own `index.html` with the app's own
Vite, React and Tailwind, and swaps the Tauri modules (`@tauri-apps/api/core`, `event`, the
plugins) for `scripts/screenshots/mock/`. The fake backend answers every command of the app's
`src/lib/api.ts` with demo data: a connected Launchpad X, three pages, a fader, OBS and
Streamlabs with a few scenes. `capture.ts` opens a fresh page per shot with Playwright
(Windows platform labels, 2× pixels, dialogs grown to full height), runs the scenario and saves
the PNG. Nothing is written into the app checkout.

If a capture fails after an app update, the usual cause is a changed label or structure that a
scenario clicks on (`scripts/screenshots/shot.ts` holds the shared moves), or a new backend
command the fake does not answer.
